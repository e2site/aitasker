# SKILL.md — aitasker

## 1. Назначение проекта

**aitasker** — десктопное Electron-приложение для управления задачами и планами с AI-агентом через MCP (Model Context Protocol). Стек: TypeScript, React, Tailwind CSS, SQLite, Electron.

Основные сущности: **проекты** → **задачи** → **планы** (с открытыми вопросами, расширениями и доработками).

---

## 2. Работа с MCP AITasker в этом проекте

MCP-сервер AITasker запущен локально. Агент работает только через MCP-инструменты — никаких прямых SQL-запросов или правок файлов базы данных.

Стандартный порядок сессии:
1. `activate_project` → проверить карточку
2. Найти или создать задачу
3. Прочитать задачу и план
4. Работать с планом (save/extend/improve)
5. Менять статус задачи по ходу работы

---

## 3. Активация проекта и проверка карточки

```
activate_project({ projectRef: "project-general" })
```

`projectRef` — это ID (`project-general`) или название (`aitasker`).

После активации проверить через ответ: заполнены ли `rootPath`, `languages`, `skillFilePath`, `description`. Если нет — обновить через `update_project_profile`.

```
update_project_profile({
  projectId: "project-general",
  rootPath: "G:/code/aitasker",
  languages: ["CSS", "HTML", "JavaScript", "TypeScript"],
  skillFilePath: "G:/code/aitasker/SKILL.md"
})
```

---

## 4. Создание задач через MCP

```
create_task({
  title: "Короткое название задачи",       // минимум 3 символа
  description: "Подробное описание..."     // минимум 12 символов
})
```

Обязательные поля: `title`, `description`. Задача создаётся в активном проекте автоматически. После создания сразу доступны `task.id` и начальный статус `new`.

---

## 5. Поиск задач, чтение задачи и плана

Найти по тексту:
```
find_tasks({ query: "часть названия" })
```

Прочитать задачу и план целиком:
```
get_task({ taskId: "uuid" })
```

Прочитать только план (с расширениями и доработками):
```
get_plan({ taskId: "uuid" })
```

---

## 6. Создание и обновление плана

```
save_plan({
  taskId: "uuid",
  contentMd: "# Заголовок\n\n## Шаги\n...",
  source: "agent",           // "agent" или "human"
  openQuestions: []          // необязательно
})
```

`save_plan` создаёт новую ревизию. Использовать только когда план существенно меняется. Для уточнений и решений в ходе работы — использовать `append_plan_extension` / `append_plan_improvement`, а не новую ревизию.

---

## 7. Открытые вопросы

Открытые вопросы передаются **отдельно** от markdown-текста плана — в поле `openQuestions: string[]`:

```
save_plan({
  taskId: "uuid",
  contentMd: "...",
  openQuestions: [
    "Какой фреймворк использовать для таблицы?",
    "Нужна ли пагинация?"
  ]
})
```

Пока у задачи есть открытые вопросы, смена статуса через UI заблокирована (кроме `requires_clarification`). Через MCP статус можно менять свободно.

---

## 8. Ответы на открытые вопросы

```
answer_plan_question({
  taskId: "uuid",
  questionId: "question-uuid",
  answer: "Используем @tanstack/react-table, пагинация не нужна."
})
```

После ответа вопрос закрывается и переходит в обсуждение плана. Когда все вопросы закрыты — UI снова разрешает менять статус.

---

## 9. Расширения и доработки плана

Используются для переписки по задаче без создания новой ревизии.

**Расширение** (`append_plan_extension`) — дополнительный контекст, уточнение требований, новые сценарии:
```
append_plan_extension({ taskId: "uuid", content: "Текст расширения..." })
```

**Доработка** (`append_plan_improvement`) — замечания по реализации, фиксация решений, баги:
```
append_plan_improvement({ taskId: "uuid", content: "Текст доработки..." })
```

`author` по умолчанию `"agent"`. Для записи от имени пользователя: `author: "human"`.

---

## 10. Точечное чтение обсуждения

Вместо чтения всего плана можно прочитать конкретный комментарий по ID:

```
get_plan_extension({ taskId: "uuid", extensionId: "comment-uuid" })
get_plan_improvement({ taskId: "uuid", improvementId: "comment-uuid" })
```

ID приходит в сообщении от пользователя или из `get_plan`.

---

## 11. Сжатие переписки в план

После накопления расширений и доработок — объединить всё в один цельный план и очистить блоки переписки:

```
consolidate_plan_discussion({
  taskId: "uuid",
  contentMd: "# Обновлённый план\n\n...",
  source: "agent",
  openQuestions: []   // если открытых вопросов нет
})
```

Вызывать после того как переписка содержательно обработана и план полностью актуален.

---

## 12. Статусы задач

| Статус | Описание |
|---|---|
| `new` | Только создана |
| `planning` | Идёт планирование |
| `requires_clarification` | Нужны уточнения (открытые вопросы) |
| `implementation` | В реализации |
| `completed` | Завершена |

Менять статус:
```
update_task_status({ taskId: "uuid", status: "implementation" })
```

Через UI смена статуса **заблокирована** пока у задачи есть открытые вопросы — кроме перехода в `requires_clarification`. Через MCP ограничений нет.

---

## 13. Практические правила

1. **Сначала читать, потом менять.** Перед правкой плана вызвать `get_task` или `get_plan`.
2. **Не плодить ревизии.** `save_plan` — только для существенных изменений плана. Для заметок в ходе работы — `append_plan_extension` / `append_plan_improvement`.
3. **Фиксировать решения в обсуждении.** Если принято архитектурное или продуктовое решение — записать через `append_plan_improvement` до перехода к следующему шагу.
4. **Точечное чтение.** Если пользователь указал конкретный `extensionId` или `improvementId` — читать только его через `get_plan_extension` / `get_plan_improvement`, а не весь план.
5. **Статус держать актуальным.** `planning` при разработке плана, `implementation` при кодировании, `completed` после проверки.
6. **Сжимать переписку.** Если расширений и доработок накопилось много — вызвать `consolidate_plan_discussion`, чтобы план оставался читаемым.
